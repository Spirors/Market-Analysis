## P0 — user-visible latency (3-second add/delete)

**Status:** investigated; root cause confirmed; fix proposed.

**Repro:** Open the dashboard, click `+ Add holding`, enter `NVDA`,
click OK. On a cold cache (or within ~5 min of a cold load with >5
holdings), the row takes ~3 seconds to appear. Same for `+ Add cash`,
portfolio `✕` delete, rename, cash row edit/delete. Fast paths that
work today: inline cell edit (shares/cost inputs) and the tickerTable
row-level `✕` button (these don't trigger a full re-fetch).

**Red-green verification (TestClient + mocked yfinance):** With a
test portfolio of 10 holdings, the 3 yfinance call families
(`market._quote_snapshot`, `market.get_histories_bulk`,
`portfolio._info_cached`) stubbed to return instantly, and
`validation.validate_symbol` stubbed to return `valid: True`, a single
`POST /api/portfolios/{pid}/holdings` completed in
**min=23.1ms, avg=29.9ms, max=54.2ms over 5 trials**. This
confirms: the structural cost of the cache patch + mutation + JSON
serialisation is ~30ms. The ~3s observed by the user must therefore
come from the yfinance HTTP calls themselves, NOT from Python overhead
or FastAPI plumbing. The 22-call call-count analysis maps directly
to ~100-200ms per `Ticker.info` + ~500ms per bulk `yf.download` =
~3s on a cold cache.

**Where:**

| File:line | Role |
|---|---|
| `app/portfolio.py:25-57` | `_patch_dashboard_cache(state)` — best-effort cache patch |
| `app/portfolio.py:47` | **Calls `enrich_portfolios(state)` synchronously inside the cache patch** |
| `app/portfolio.py:412-465` | `enrich_portfolios` — 3 yfinance call families |
| `app/portfolio.py:440` | `market._quote_snapshot(symbols)` — bulk 7d download, **NO disk cache** |
| `app/portfolio.py:442` | `market.get_histories_bulk(symbols, days=260)` — 24h disk cache |
| `app/portfolio.py:446` | `{s: get_info_snapshot(s) for s in symbols}` — N × `Ticker.info` + `.calendar` (5-min lru_cache) |
| `app/api.py:216,235` | `holdings_add` / `holdings_edit` ALSO call `market._quote_snapshot` inline for the API response |
| `static/js/portfolio.js:392,396,273,428,437` | Bespoke button handlers that `await refresh()` after every API call |

**Why:** Every portfolio mutation (add/delete holding, add/edit/remove
cash, create/delete/rename portfolio, column prefs) fires
`_patch_dashboard_cache(state)` which calls `enrich_portfolios(state)`.
On a cold cache, `enrich_portfolios` does 1 bulk `yf.download(7d)` + 1
bulk `yf.download(260d)` + N × `Ticker.info` + N × `Ticker.calendar`.
For ~10 holdings this is ~22 HTTP calls (~3 s cold, ~2.4 s warm). The
frontend then calls `refresh()` which hits `GET /api/portfolios`,
which calls `enrich_portfolios` AGAIN (`app/api.py:189`). So every
mutation pays the enrichment cost at least twice — once server-side in
the POST response, once client-side in the follow-up GET.

**Three independent contributors** (any one would cause visible lag):

1. **`_patch_dashboard_cache` re-enriches all symbols on a 1-symbol
   change** (`app/portfolio.py:47`). Should be a targeted patch (only
   the new symbol, or none — just stamp the vintage).
2. **`_quote_snapshot` has no disk cache** (`app/market.py:94-130`).
   `get_quotes` (`app/market.py:133-142`) wraps it with QUOTE_TTL=30min
   disk cache but the portfolio path doesn't use it. Every call hits
   yfinance.
3. **Frontend `refresh()` after every mutation** (`static/js/portfolio.js:392,396,273,428,437`).
   Each `refresh()` is a full `GET /api/portfolios` → another
   `enrich_portfolios`. The tickerTable row-level callbacks already
   prove the optimistic-update pattern works (they don't call
   `refresh()`).

**Fix sketch (does NOT re-introduce documented regressions):**

- **Server side:** Change `_patch_dashboard_cache` to a *targeted*
  patch. Read the cached `portfolios` sub-tree, apply the delta for
  the affected holding only (or just bump the vintage without
  enrichment), write back. The next `GET /api/dashboard` will pick up
  the patched cached payload; the next full `refresh_market()` will
  re-enrich everything. Per the
  "Earnings cache-miss path must not trigger a full universe rebuild"
  decision (`80d0fef`), a cache-patching helper must NOT fall through to
  a full rebuild — either patch minimally or invalidate and return.
- **Server side:** Route portfolio quote lookups through
  `market.get_quotes` (disk-cached) instead of `_quote_snapshot`
  directly. Eliminates the "always cold" quote fetch on every
  mutation.
- **Client side:** Drop the `await refresh()` calls in the bespoke
  button handlers (`static/js/portfolio.js:392,396,273,428,437`).
  Optimistic local state via `p.holdings.push(...)` /
  `p.holdings = p.holdings.filter(...)` is already done by the
  tickerTable callbacks (`static/js/portfolio.js:340-360`) and works
  for card-level totals via `renderGrandHeader()`. The `refresh()`
  call is doing a full server round-trip for nothing the optimistic
  update doesn't already cover.
- **Regression test:** Mock `market._quote_snapshot`,
  `market.get_histories_bulk`, and `yf.Ticker.info` /
  `yf.Ticker.calendar` with network-independent fakes. Add a holding
  via `POST /api/portfolios/{pid}/holdings` and assert end-to-end
  latency <500 ms with N=15 holdings on a cold cache. Plus the
  optimistic-update test: mock the network, click `+ Add holding`,
  assert the row is visible within one paint frame after the POST
  resolves (no follow-up `refresh()` call). Both should FAIL on the
  current code and PASS with the fix.

## P7 — news section health check (user-reported "3 days no news")

**Status:** investigated; pipeline working correctly; the quiet timeline
is real, not a bug.

**Repro (today, 2026-09-07 18:26 UTC):** `data/events.json` has
169 total events; newest by `published` is `2026-09-04T17:23:13`
(Trump calls for interest rate cut after jobs figures). 0 events in
the last 72h. 21 events in the last 168h. Sources breakdown of
last-7d items: 15 MarketWatch + 6 BBC Business (no curated seed in
that window — the curated seed is historical 2026 timeline data).

**Where the silence comes from — three independent probes:**

1. **RSS feeds are alive.** Probed both `NEWS_FEEDS` entries today:
   - MarketWatch (`https://feeds.marketwatch.com/marketwatch/topstories/`):
     HTTP 200, 8.3 KB payload, 10 entries, 10/10 within 48h,
     newest 0.9h old.
   - BBC Business (`https://feeds.bbci.co.uk/news/business/rss.xml`):
     HTTP 200, 38 KB payload, 52 entries, 11/30 within 48h,
     newest 2.0h old.
   Both feeds parse cleanly (`feedparser.bozo = False`). Not a feed
   outage.

2. **The strict threshold filters out most of what comes in.** Ran
   `app.news.analyze()` on all 21 live 48h items via the same path
   `fetch_and_store()` uses (`app/news.py:336-421`). `IMPORTANCE_THRESHOLD`
   is **6.0** (`app/news.py:128`). Of the 21 items:

   | Composite | Count | Examples |
   |---|---|---|
   | ≥6.0 (would ingest) | **1** | "Is the stock market open today for Labor Day? What about bond trading" (comp=8.28) |
   | 2.0-3.5 | 2 | "Chip stock investors beware…" (comp=3.6); "China to pump $54bn into state banks" (comp=2.0) |
   | 0.0-2.0 | 18 | Lifestyle/personal-finance/UK-domestic items |

   The one item that *would* pass today is a calendar explainer
   (Labor Day market closures), not a market-moving story. Labor Day
   weekend + generally soft news flow explains the gap.

3. **Scheduler cadence appears healthy.** `first_seen` newest =
   `2026-09-04T17:56:03` (3 days stale — consistent with the 1 item
   passing threshold in last 168h). `updated_at` newest =
   `2026-09-07T18:23:56` (today) — touched within minutes of the
   probe, evidence the news refresh pipeline is touching the file
   on schedule even when it finds nothing new. `NEWS_REFRESH_INTERVAL_HOURS = 4`
   (`app/config.py:314`); the news task uses `PT4H` repetition
   (`app/scheduler.py:228`).

**Why — the mechanism in 1-2 sentences:** The news pipeline is
strict by design — it only ingests items scoring ≥6.0 on a
keyword-weighted composite (with a `FINANCE_RELEVANCE_BOOST` of 1.5x
for finance-specific items). The MarketWatch top-stories feed and
BBC Business feed are general-purpose outlets whose headlines skew
toward lifestyle/personal-finance/UK-domestic stories; only a small
fraction cross the threshold. Over the last 168h (one full week)
only 21 of ~150 published items passed; in the last 72h only 1.
The silence on the dashboard reflects this filtering correctly.
